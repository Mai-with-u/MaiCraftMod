# 领域规格：技能发布

> 状态：已批准（2026-10-18）。玩法技能全部随 Mod 发布，直播策略留在宿主。
> 范围：MCP 资源接口与随包的玩法技能。不改变角色在游戏里的行为，只改变资料从哪来、谁能读。
> 依据：MCP Skills extension（`io.modelcontextprotocol/skills`，SEP-2640，Final）与 Agent Skills 规范。
> 边界：本规格定义 Mod 侧怎么发布技能；宿主怎么合并、展示、回退由宿主自己的技能文档定义。

## 1 问题

MaiCraft 现在有两种写给模型看的资料：能力说明回答"这个能力怎么调"，知识库回答"世界里的事实是什么"。缺第三种：**一类事该怎么做成**——阶段顺序、决策点、常见坑、什么时候查哪份资料。这种文档原来放在宿主 Amaidesu 的仓库里，由宿主按能力清单筛。

这样有三个问题：

- 技能和能力分在两个仓库，能力名、参数、知识地址改了，技能不会跟着改，只能靠人记得核对。
- 宿主得先读回能力清单和模组清单，再自己决定哪些技能进目录；判断散在宿主。
- MaiCraft 作为独立的 MCP 服务器，别的客户端连上来拿不到这套玩法经验。

## 2 定位

三层的分工不变，只把第三层换个发布方：

| 层 | 回答什么 | 谁发布 | 放在哪 |
| --- | --- | --- | --- |
| 能力说明 | 这个能力怎么调、参数是什么、结果怎么读 | Mod | `assets/maicraft/abilities/` |
| 资料 | 这个世界里的事实：配方、机制、思索、任务书 | Mod | `lookup(topic=knowledge)` |
| 技能 | 一类目标怎么一步步做成，遇到岔路怎么选 | Mod | `skill://` 资源 |

技能是**文档**，不是能力，也不是替模型做决定的代码。长线目标仍由模型规划；技能只是把它已经会用的能力按经验排个先后。

## 3 内容归属

| 内容 | 放哪 | 例子 |
| --- | --- | --- |
| 阶段顺序、完成标准、决策点、常见坑、该查哪份资料、许可怎么设、能力怎么组合 | Mod | 从空手到石器的开局；Create 机器的工艺 → 蓝图 → 施工 → 动力 → 试运行；打龙的准备与分段 |
| 什么时候上报、直播节奏、观众体验、什么时候问主播、人格与说话方式、宿主工具（`minecraft_report`、`minecraft_notebook`） | 宿主 | 每完成一段汇报；不要原地等天亮；拿不准问主播 |
| 某个能力的参数逐项说明、配方与掉率 | 原处 | 能力说明、知识库；技能只引用，不复制 |

写进 Mod 的技能必须是**宿主中立**的：不出现"主播""直播""观众""上报主播"，不出现宿主的工具名。需要请示或许可时，说"需要许可/确认"或"把现场写进结果"，不假设调用方是谁。

## 4 接口

### 4.1 握手

`initialize` 的能力声明在 `tools` 之外加 `resources`（空对象）。只有随包技能非空时才声明。`instructions` 末尾加一句：

> 本服务器还发布玩法技能：用 `resources/list` 查看可用技能，用 `resources/read` 读 `skill://<分类>/<名字>/SKILL.md`；技能是参考，不授予额外权限。

暂不声明 `io.modelcontextprotocol/skills` 扩展：它要求 MCP `2026-07-28` 修订版与 `skills/list`、`skills/get`，而当前服务器支持到 `2025-11-25`。在此之前，`skill://` 按普通资源发布，任何支持 `resources` 的客户端都能读。

### 4.2 `resources/list`

不带分页，一次给全部当前适用的技能：

```json
{
  "resources": [
    {
      "uri": "skill://survival/survival-opening/SKILL.md",
      "name": "survival-opening",
      "description": "生存开局：从空手到有石器、食物、床和据点的稳定状态；新世界或身上几乎没东西时先读",
      "mimeType": "text/markdown"
    }
  ]
}
```

按 URI 排序。装了对应模组才适用的技能不在列表里；没装模组时列表少几项，不是错误。

### 4.3 `resources/read`

参数 `uri`，返回原样的 `SKILL.md`（含 frontmatter）：

```json
{
  "contents": [
    {
      "uri": "skill://survival/survival-opening/SKILL.md",
      "mimeType": "text/markdown",
      "text": "---\nname: survival-opening\n...\n---\n\n# 生存开局\n..."
    }
  ]
}
```

不认识的地址、不适用于本实例的技能，按 JSON-RPC `-32602`（Invalid params）报错，消息写明没有这项技能。不拿相近的顶替。

`resources/templates/list` 返回空列表，给那些每次连接都会问一遍模板的客户端。

### 4.4 地址

```text
skill://<分类>/<名字>/SKILL.md
```

- 分类是组织用的路径前缀，例如 `survival`、`create`、`mekanism`、`progression`、`building`。
- 最后一段必须等于 `SKILL.md` 里的 `name`；读的人不用打开正文就能从地址认出技能名。
- 不提供目录读取（`resources/directory/read`），技能只有 `SKILL.md` 一个文件。

### 4.5 不放进资源的东西

知识库仍走 `lookup(topic=knowledge)`，不列进 `resources/list`：资料按需搜索、分页和来源状态都在 `lookup` 里，搬进资源会多一套入口。能力说明也不进资源，它随 `lookup(topic=abilities, id=…)` 读。

## 5 文件与格式

### 5.1 位置

```text
assets/maicraft/skills/index.txt                 一行一个技能，写 <分类>/<名字>
assets/maicraft/skills/<分类>/<名字>/SKILL.md     一篇技能
```

`index.txt` 是唯一的清单：没写进去的文件不发布；写了但文件不在、名字对不上、分类对不上，启动时直接失败。空行和 `#` 开头的行跳过。

### 5.2 frontmatter

用 YAML 的一个严格子集：只认 `name`、`description`、`metadata` 三个顶层字段，其余顶层字段报错。

```markdown
---
name: create-machine-workflow
description: 机械动力机器：从产物定工艺、读资料、画蓝图、施工、接动力到试运行；要造一台 Create 机器或让它出货时读
metadata: {"requires-mods": "create"}
---

# 正文……
```

- `name`：小写字母、数字、连字符，1–64 字，不能以连字符开头或结尾，不能有连续连字符；必须等于技能目录名。
- `description`：1–1024 字，先说是什么，再说什么时候读；它是 `resources/list` 里唯一的信息，决定模型会不会去读。
- `metadata`：一行 JSON 对象，值只能是字符串；`requires-mods` 是逗号分隔的模组 ID，全部装了这项技能才发布。没有前提时整个字段可以省略。
- 正文是写给模型的 Markdown，用第二人称、短句、表格；控制在一屏到两屏。
- 引用能力用 ID（`maicraft:obtain`），引用工具用 MCP 的短名（`lookup`、`execute`、`goal`、`events`、`observe`），引用事实用知识地址（`maicraft://knowledge/...`）。不写宿主改名后的 `maicraft_lookup`。

### 5.3 解析失败

frontmatter 缺字段、多字段、名字不合规、正文为空、索引重复、文件缺失，都在建技能库时抛出，游戏启动时暴露，不把空正文当技能交给模型。

## 6 门控

只看 `requires-mods`：这些模组 ID 在本局都登记为可用（联动模组真的接上了，不只是装了）时，技能进列表、可读；否则不进列表，读也报没有。

不按能力门控。能力在进世界时才登记，MCP 服务在启动时就起来了；按能力筛会让启动时读到的目录是空的。能力名写错由技能内容的测试和审阅兜住。

## 8 宿主分工

宿主侧（Amaidesu）保留一份本地"直播与上报"技能，写什么时候用 `minecraft_report`、直播节奏、观众体验、什么时候问主播、人格与口吻。玩法技能不再在宿主仓库里重复。

宿主连接 MaiCraft 后：

- 读 `resources/list` 得到远端技能目录，与本地技能合并；目录里标明来源。
- 读正文走 `resources/read`；读回的内容按外部输入对待，标明来自 MaiCraft。
- 连接断掉时回退到本地技能；远端玩法技能暂时不可用，如实告诉模型。
- 技能正文里的 `lookup`、`execute`、`goal`、`events`、`observe` 对应宿主暴露的 `maicraft_lookup`、`maicraft_execute`、`maicraft_goal`、`maicraft_events`、`maicraft_observe`，由宿主在技能段里说明。

## 9 测试与验收

**离线**：

1. 索引里的每一篇都加载；URI、名字、分类、描述对得上。
2. 不装 Create 时 Create 两项不在列表、读报 `-32602`；装 Create 时出现。Mekanism、FTB 任务同理。
3. `resources/read` 返回的正文和文件逐字一致；不认识的地址报错，不拿相近的顶替。
4. 索引重复、文件缺失、frontmatter 缺字段/多字段、名字带下划线或与目录不一致、正文为空，构造技能库时失败。
5. 传输层：握手声明 `resources`；`resources/list`、`resources/read`、`resources/templates/list` 的返回形状；未知 URI、缺 `uri` 的错误码。
6. 没有技能资源的服务不声明 `resources`，旧的传输测试不受影响。

**实机**：

1. 客户端连上后 `resources/list` 看得到这个实例适用的全部技能；装了 Create 的实例看得到 Create 两项，装了 Simulated 的看得到载具一项。
2. 读一篇的技能正文，模型按里面的工具名能直接调 `lookup`、`execute`。
3. Amaidesu 连上后，技能目录里同时有本地"直播与上报"和远端玩法技能；拔掉 MaiCraft 后远端消失、本地还在。

## 10 不做

- 不实现 `skills/list`、`skills/get` 和内容摘要（SHA-256）：等服务器支持 MCP `2026-07-28` 再补；现在按普通资源发布。
- 不实现 `resources/directory/read`：一篇技能只有一个文件。
- 不把知识库、能力说明改成资源。
- 不在 Mod 里写直播策略、上报方式、人格或宿主工具名。

## 11 需登记的名字

| 中文 | 代码 / MCP | 意思 |
| --- | --- | --- |
| 技能 | `Skill`、`SkillLibrary` | 写给模型的玩法经验文档，随 Mod 发布，经 `skill://` 读取；不是能力，也不是工具 |
| 技能资源 | `McpResources` | MCP 资源层的通用出口：列资源、按地址读；技能库实现它 |
| 技能地址 | `skill://<分类>/<名字>/SKILL.md` | 一项技能的 `SKILL.md` 的地址 |
| 前提模组 | `metadata.requires-mods` | 这项技能要哪些联动模组都接上才发布 |
