# 11 游戏内测试（GameTest）

游戏内测试是 Minecraft 自带的自动化测试框架 GameTest：每个测试在真实服务端世界的一块独立小场景里跑，断言世界状态，断言失败或超时即失败。跑测试的引擎（划地皮、清空、封边界、超时判定）是原版的；Mod 测试类的注册与发现由加载器扩展（NeoForge 扫描 `@GameTestHolder` 注解类，Fabric 走 `fabric-gametest` entrypoint，差异见「边界」）。

## 三层测试各管什么

| 层 | 跑在哪 | 测什么 | 够不着的 |
| --- | --- | --- | --- |
| 离线测试 `:common:test` | 纯 JVM，Minecraft 不在场 | 判断逻辑、任务阶段走向，世界与交互全是替身 | 替身是我们的约定，原版逻辑不执行：Mixin 注入点对不对、原版方法被谁覆写，原理上测不到 |
| 游戏内测试 `:neoforge:runGameTestServer` | 真实服务端进程 | 服务端链路（Mixin 钩子、按服务器实例登记的服务、协议操作）与真实游戏代码待在一起对不对 | 测试服务端无画面，客户端行为层驱动不了 |
| 实机验收 | 真实客户端 + LLM 经 MCP 驱动 | 端到端，含客户端行为层（任务、能力、观察呈现）与决策质量 | 慢、非确定，需要人与看守纪律 |

三层各测下一层够不着的东西，互相不可替代。放床漏记归属就是活例子：离线测试抓不到（替身不知道 BedItem 的存在），游戏内测试第一个样板就抓到了，实机要等有人放床又恰好查归属才暴露。

## 客户端内容为什么测不了

GameTest 的驱动引擎是服务端世界，客户端内容卡在两道坎上，换加载器也一样：

1. **headless 测试服务端里，客户端代码不在场。** 专用服务器进程上 Mod 只走服务端启动路径——玩家行为层、能力、交互与感知、MCP 入口这些客户端代码根本没有被创建，不是"测不到"，是"不在场"。
2. **在真客户端里跑，框架驱动的仍是服务端。** 原版支持在单人客户端里用 `/test` 命令跑 GameTest，但驱动的是集成服务端：测试的 mock 玩家是服务端 `ServerPlayer`，对面没有真客户端，没有键鼠、容器界面与客户端预测，原版交互确认链整个不参与；测试代码跑在服务端线程，而角色的本体是客户端线程上的本地玩家（所有游戏状态只在客户端线程读写），跨线程驱动违反线程规则。

生态里唯一的真客户端测试是 Fabric 新版的 client gametest api（1.21.5+，模拟键鼠、验证画面），NeoForge 至今没有；本项目钉在 1.21.1，两边都用不上。所以"角色行为"这类端到端验证继续归实机；给实机降本的正路是把启动、存档重置、背包与方块对账这些机械部分脚本化，不在 GameTest 里。

## 什么时候写

- **新增或修改服务端链路：测试随代码走**，核对场景随同一工作包交付，最好先写核对看它红、再接线看它绿。领域规格第 9 节列出的服务端场景，归宿就是这里的游戏内测试。
- **存量链路按风险补**：真实事故史（哪些链路坏过）与组装接线层（替身原理上够不着、又没有实机盯着的地方）优先。
- **长尾跟事故补锚**：实机暴露的问题归类后，根因落在服务端链路的，修复提交里顺手固化一个场景当回归锚；不为低风险的长尾预写。

## 跑法

```bash
./gradlew :neoforge:runGameTestServer   # NeoForge：系统属性 neoforge.gameTestServer 开测试服务端
./gradlew :fabric:runGametest           # Fabric：fabric-api 的 gametest 开关换掉专用服务器入口
```

起一个无画面的专用服务端（超平坦、无刷怪、每次全新世界，不碰任何存档；NeoForge 世界目录 `neoforge/run-gametest/`、Fabric 世界目录 `fabric/runs/gametest/`，都被忽略），跑完注册的全部测试自动退出；有失败构建变红，退出码是失败的测试数。全程约半分钟，改到哪测哪，不必等全量构建。

## 写一个测试

1. 核对动作写进 common 的 gametest 源集（`common/src/gametest/`），两个加载器的入口类各留一行委托；样板见 `BlockOwnershipGameChecks` 与 `ServerLinkGameChecks`。加载器侧：NeoForge 测试类在 `neoforge/src/gametest/`，标 `@GameTestHolder("maicraft")` 与 `@PrefixGameTestTemplate(false)`；Fabric 测试类在主源集 `fabric/src/main/java`，加进 fabric.mod.json 的 `fabric-gametest` entrypoint。
2. 驱动走公开入口，与实机同路：造真实的服务端玩家（`GameTestHelper.makeMockServerPlayerInLevel`）、走原版的放置与破坏路径、按协议信封调服务端操作，不绕过分层去戳内部。改全局服务（`ServerLinkServices` 换记录式确认通道那类）要在同一个服务器刻里换入、动作、断言，不跨刻，免得撞上启动在刻末的重新登记。
3. 场景在测试里程序化搭建，坐标用 helper 的相对坐标（相对测试区原点），必须装得进模板声明的尺寸。
4. 断言失败用 `GameTestHelper.fail` 带一句人话；等待与延时用 helper 的调度方法（`runAtTickTime` 等），不起线程。

## 结构模板

模板声明测试区的尺寸（宽 x 高 x 深），框架按它划地皮、清空、封屏障；场景内容在测试代码里搭。它是框架的核心概念，不是我们的仪式：测试方法必须有模板，缺了启动即崩（框架按模板知道在哪划多大的地、初始状态是什么）。

- **按尺寸共用**：全项目每个尺寸只留一份空模板 `data/maicraft/structure/empty<w>x<h>x<d>.nbt`。测试类关掉类名前缀（`@PrefixGameTestTemplate(false)`）、方法上写 `template` 名；不写 `template` 时框架按"类名.方法名"找模板，一个测试一个文件，不用那种做法。
- **生成**：`python tools/gen_gametest_template.py empty16x12x16 --size 16,12,16`。新测试装得进既有尺寸就用既有的，装不进再生成更大的，模板总数保持一小串尺寸。
- **需要露天的测试**（阳光、白天判定）同一份模板，注解加 `skyAccess = true`——那只是封边界时留不留天顶，不改变盒子大小。
- **只认二进制**：1.21.1 的资源包结构模板只认 gzip 压缩的二进制 `.nbt`（不认文本 `.snbt`），编辑器打开是乱码，这是原版限制。改动一律重新生成，不手编。
- IDE 的 NBT 查看器对外部脚本重新生成的文件不自动刷新：显示旧内容时先关闭标签重开或 Reload from Disk，再怀疑文件本身。

## 已知坑

| 坑 | 处置 |
| --- | --- |
| 服务端上放置成功返回 `CONSUME` 不是 `SUCCESS`（`sidedSuccess` 按端取值） | 判定用 `consumesAction()`，不判枚举相等 |
| mock 玩家的碰撞箱挡住要放的格子，原版判无处可放 | 玩家挪到测试区角落再动手 |
| 不写 `template` 时模板路径拼上方法名，方法名被资源路径约束 | 方法上都写 `template`，用共享模板 |
| 升 Minecraft 版本后模板读不出来 | 生成脚本里的 `DataVersion` 常量要跟着版本改（1.21.1 是 3955） |

## 边界

- **两个加载器都接了**，共享核对动作与空模板在 common 的 gametest 源集（`common/src/gametest/`，不进发布的 Jar），加载器差异只有两处：
  - 注册：NeoForge 扫描 `@GameTestHolder` 注解类；Fabric 走 `fabric-gametest` entrypoint（fabric.mod.json），由 fabric-api 扫描方法。
  - 模板名：NeoForge 自动补 Mod 命名空间，写裸名 `empty9x7x9`；Fabric 不补，要写全 `maicraft:empty9x7x9`。测试方法各自在加载器的入口类里，都是薄委托。
  - Fabric 的测试入口按其惯例在主源集、随 Jar 发布（entrypoint 在生产环境也要能解析），没有被测试运行用到时不做事。
- 一轮全绿只证明"这些链路在真实服务端上行为正确"，不等价于实机验收通过；证据标准与汇报格式仍按 05 执行手册。
