# 07 对外接口（MCP）

对外接口是 LLM 认识这个角色的唯一途径。它要做到两件事：**LLM 不用读说明书就能猜对怎么用**，以及**LLM 能看到玩家看到的东西**。v0 两件都没做好（见 01 症状 9，以及 00 第 1、2 层的发现）。

接口的使用方有两个：

- **LLM**：通过 Amaidesu 宿主调用，宿主会把工具改名为 `maicraft_*`；
- **宿主程序**：开局读取状态、等待任务事件、分页回读结果。

v1 为这两个使用方分别设计，不再让一个工具同时服务两者。

本文里的"工具"都指 **MCP 工具**（observe、lookup……），不是游戏里的镐和斧。

## 1. 设计原则

1. **一个工具只做一件事；一个参数只有一种含义。** v0 的 `perceive` 一身兼五职（观察、查能力、查知识库、上网、等事件），`focus` 一个参数有六种含义。
2. **名字脱离上下文也不会被读成别的意思。** LLM 往往只看字段名就动手；字段名、枚举值、问题种类都按 [09-命名与术语](09-命名与术语.md) 的原则起名，例如问题种类不用 `NEED_TOOL`（会被读成"需要调用另一个 MCP 工具"）。
3. **工具描述里不写具体能力的特例。** 某个能力的用法只写在它自己的能力说明里。
4. **平铺的 schema，不用 `anyOf` / `oneOf`。** 已经实测有宿主（MiniMax）解析不了 `anyOf`。要表达"多选一"，就拆成两个工具或两个字段。
5. **藏执行细节，不藏观察事实。** 路线、点击、槽位不给 LLM；看到的东西是什么、在哪、怎么指着它，全部给。
6. **同一个概念全接口只有一个名字**（第 5 节参数名表）。
7. **所有工具用同一个返回格式**（第 6 节），所有能力用同一个任务结果结构（第 6.1 节）。
8. **默认值就是正常玩家会做的事**：许可用 M7 的默认值；数量、范围有合理默认；布尔参数默认 `false` 时表示"不做特别的事"，不用布尔参数表示许可。

## 2. 工具集

| 工具 | 给谁 | 做什么 | 取代 v0 |
| --- | --- | --- | --- |
| `observe` | LLM | 看世界和自己：角色状态与背包、周围场景、某个看到的东西的细节、世界记忆、角色眼里此刻的画面（一张图） | `perceive` 的 situation / surroundings / landmarks / exploration |
| `lookup` | LLM | 查资料：能力列表与能力说明、离线知识库、Minecraft Wiki、配方 | `perceive` 的 abilities / knowledge / web_knowledge |
| `execute` | LLM | 开始做一件事（下达一个目标）；`dry_run=true` 只检查、估算，不动手 | `execute` + `plan` |
| `goal` | LLM | 查看、暂停、恢复、取消下达过的目标，回答目标提出的问题，分页读证据 | `task` |
| `events` | 宿主（也可开放给 LLM） | 按游标读角色身上发生的事（目标的进展、临时任务、角色死了）与聊天，没有新事件时可以等一会儿 | `perceive(view=attention)` |

依然是 LLM 面对 4 个工具，但每个都只做一件事。

- `execute` 不是 Minecraft 的 `/execute` 命令；要发命令或聊天，用能力 `chat`。工具描述里写明这一点。
- 读任务事件的工具叫 `events`，不叫 `wait`：`wait` 读起来像让角色在游戏里站着等，宿主那边也常有一个让出一轮的同名工具，同名会让 LLM 分不清。

一些 v0 里塞在 `perceive` 里的**领域分析**（施工场地勘测 `construction_site`、Create 动力源 `kinetic_sources`、机器界面、探索目录），改为**只读能力**，通过 `execute` 调用并当场返回报告。它们有自己的参数和能力说明，不再污染观察工具的参数表。原则是：**`observe` 只管"玩家此刻能看见什么"；需要分析、计算的，都是能力。**

### 2.1 `observe`

| 参数 | 含义 |
| --- | --- |
| `what` | `self`（生命、饥饿、背包、装备、当前任务一句话、当前许可）、`scene`（周围场景，默认）、`detail`（一个看到的东西的细节）、`places`（只列记住的地点、建筑机器档案名与地盘，以及自动记录分类条数）、`world_memory`（角色记得的地点、容器、见过的资源与结构；不是对话记忆）、`menu`（此刻开着的界面）、`picture`（角色眼里此刻的画面，一张图） |
| `id` | 只在 `what=detail` 或 `picture` 时用：观察编号（`e12`、`f3`、`b5`、`s2`）或地标名；`picture` 还收建筑档案名（转过去看那一栋） |
| `grid` | 只在 `what=scene` 时用：`true` 时附带近处的俯视网格（原 `LookAroundTool`） |
| `radius` | 只在 `what=world_memory` 时用：只列离角色这么近（格，同一维度）的记录 |
| `kind` | 只在 `what=world_memory` 时用：只列这一类记录（`container` / `workstation` / `site` / `machine` / `building` / `temporary_block`） |
| `with_menu` | 只在 `what=picture` 时用：`true` 时连同此刻开着的界面一起拍（整幅屏幕画面）；界面认不出、结构化读不出来时用 |
| `unlabeled` | 只在 `what=picture` 时用：`true` 时图上不标观察编号（看外观时用）；编号和它们在图上的位置照样列在 `in_picture` |
| `sections` | 只在 `what=world_memory` 时用：只取哪几节的列表（`places` 记住的地点、`regions` 圈的地盘、`records` 容器与见过的资源）；不给就三节都给。记住的容器与资源记录会随游玩一直变长，只要某一节的调用方按节取，避免整包顶到回包上限 |

返回内容见第 7 节。

### 2.2 `lookup`

| 参数 | 含义 |
| --- | --- |
| `topic` | `abilities`（默认）、`knowledge`、`wiki`、`recipe` |
| `id` | 精确条目：能力 ID、资料地址，或物品 ID（`topic=knowledge` 读它的物品资料页，`topic=recipe` 查它的配方） |
| `query` | 关键词搜索；与 `id` 二选一，`topic=recipe` 例外：与 `id` 同给时按词过滤那一页（只留产出或原料沾词的）。`topic=recipe` 只给 `query` 时按名字找物品 ID；`topic=wiki` 时按条目标题搜 |
| `url` | 只在 `topic=wiki` 时用：读一篇条目（Minecraft Wiki 的 `/w/条目名`，或 MC百科的 `/item/`、`/class/`、`/post/` 页面） |
| `uses` | 只在 `topic=recipe` 时用：`true` 查能拿它做什么、它当工作站能做什么；不给时查怎么做出它。命中太多的一段只回总数与缩窄建议 |
| `offset` | 只在 `topic=wiki` 读 `url` 时用：从第几段读起，照抄上一页的 `next_offset` 或 `sections` 里那一节的 `offset`；不给从 0 起 |

不带 `id` / `query` 的 `lookup()` 返回全部能力的一行签名：名称、用途、参数名与类型，参数行里还带着这个参数能取的值——选项参数列出全部可选值（`operation: string (look / crouch / swing)`），数值参数写出上下限（`count: integer (1..64)`），照着填就不会被参数校验拒下。宿主开局可以直接把它放进上下文。列能力时顶上多一项 `installed_mods`：这局联动登记表里真正登记上、还开着的模组 ID（按字母排，不列版本、不列没装的；没进世界时按登记表此刻的样子给），宿主可以据此判断模组相关能力可不可用；随包的玩法技能由服务端自己按它筛选。

`topic=knowledge` 查资料：随包的游戏机制常识（只讲游戏规则，让角色去做时看对应能力的说明）、物品资料页、本实例的群系与结构目录（`id=biomes`、`id=structures`）、联动模组登记的资料（思索、任务书……）。正文与各来源的写法见 `领域/知识检索-规格.md`。

- 不带 `id` / `query`：返回目录 `knowledge`，每篇一行 `id`（资料地址）、`title`、`summary`；目录只列常识与各来源的索引，最后附 `sources`：各来源此刻的现状（一来源一句，没列出来的就是这个实例没有）；
- `query`：按标题、一句话说明和检索词找，覆盖各来源的全部条目（物品按名字与 ID、思索场景、任务书条目），问句不带空格也行，命中多的排前面；`next` 建议读排在最前的那篇，没找到时建议列出目录；
- `id`：读一篇，返回 `id`、`title`、`text`；完整地址、末段名（例如 `food`）或物品的注册 ID（例如 `create:mechanical_mixer`，读它的物品资料页）都行，按哪篇读的写进 `notes`；没有这篇时报 `unknown_id`。
- 物品资料页、群系与结构目录、模组的资料要读游戏现场：角色不在世界里时只查得到随包常识，`notes` 里如实说明。
- 物品、方块、实体、群系、结构的 ID 写错（能力参数与 `topic=recipe` 的 `id`）时，报错统一说成"物品 minecraft:diamon 不存在；你是不是要 minecraft:diamond"，本实例里找不到相近的就只说不存在。

`topic=recipe` 查配方，要在世界里（不在时报 `not_in_world`）：

- `id` 给物品 ID：配方页 `{item, name, read_from, recipe_count, categories}`，按配方类别分组，每组 `category`、`category_name`、`workstations`（在哪做）、`recipes`；每条配方 `recipe`（配方 ID，查看器给不出时为 `null`）、`inputs`、`catalysts`（有才给）、`outputs`（标了几率才带 `chance`）、`definition`（游戏里的原始定义，原样给）；
- `id` 再加 `query`：按词过滤那一页，只留产出或原料沾词的配方（全部词都要沾到，匹配配方 ID、名字与标签；过滤后一条不剩时 `notes` 里说一句）；
- 加 `uses=true`：用途页，`as_ingredient`（当原料或催化剂）与 `as_workstation`（当工作站，机器能做的加工在这里）两部分，按类别分组，每条配方压成一行（配方 ID：产出 ← 原料），不带原始定义；
- 一段命中太多（超过 100 条）时只回 `{read_from, recipe_count, note}` 与缩窄建议，不逐条列；给 `query` 换更具体的词，或直接查某一件产出物的配方页；
- `query` 给名字：`items` 列出名字或 ID 对得上的物品，`next` 建议读第一个的配方页；
- 配方一次只读一个来源：EMI、JEI 这类配方查看器，都答不了时读游戏配方表（看得到原料与产出，看不出在哪台机器上做）；`read_from` 写实际读的那个，跳过了谁、为什么写进 `notes`；物品不存在报 `unknown_id`。

`topic=wiki` 联网查 Minecraft Wiki（中文站、英文站）与 MC百科，只去这三个站；在 MCP 请求线程上联网，不卡游戏。网页是外部资料，可能过时、可能和本整合包的版本对不上，只当参考；随包资料、思索、配方读不到时再查网。来源、期限、限流、缓存与正文写法见 `领域/知识检索-规格.md` 第 11 节。

- `query` 给标题：查询里有汉字搜中文站，否则搜英文站（MC百科不让程序搜索，只能按地址读）。返回 `site`、`query`、`total`（标题对得上的总条数）、`results`（最相关的三条，每条 `title`、`url`、`summary` 开头一句；没读到开头一句的不带 `summary`，原因写进 `notes`）、`minecraft_version`（本实例的版本）；`next` 建议读第一条。搜不到时 `results` 为空，`notes` 建议换个说法再查；
- `url` 给条目地址：百分号编码与直接写中文是同一篇，章节锚点去掉，Wiki 条目名里的空格当下划线。返回 `site`、`url`、`title`、`minecraft_version`、`sections`（全篇章节目录，每节 `heading` 与 `offset`）、`paragraphs`（这一页的段落：标题段以 `#` 开头，表格一行写成 `| 格 | 格 |`）、`offset`、`total`（总段数）；一页约 16000 字、至少一段，还有下一页时给 `next_offset`，`next` 照抄就是下一页。图片不转文字，原文有图时 `notes` 说一句；
- 白名单外的地址按 `invalid_parameter` 回，`fields` 写明能读哪几种；站点上没有这一篇按 `unknown_id`；同时在做的联网查询满了（最多 2 个）按 `busy`；联网查询关着、连不上、10 秒内没查完、站点不让读、页面读不出按 `unavailable`，message 写明是哪一种并建议先用随包资料、思索、配方。开关是启动参数 `maicraft.lookup.wiki`（默认开，写 `-Dmaicraft.lookup.wiki=false` 关掉）。

### 2.3 `execute`

| 参数 | 含义 |
| --- | --- |
| `goal` | 目标（第 3 节） |
| `dry_run` | `true` 时只做校验和预检（原 `plan`），返回 `plan_id`、发现的问题和估算 `estimate` |
| `plan_id` | 执行一次 `dry_run` 通过的计划；与 `goal` 二选一 |
| `request_key` | 网络重试用的幂等键；不给时由 MCP 入口自动生成 |

只读能力（`mode=READ_ONLY`）在 `execute` 里当场返回报告，不控制角色，也不产生后台任务。

插一下的能力（`mode=CUTS_IN`）要控制角色，但几秒就做完：照常回 `goal_id`，不替换手上的目标，压在它上面做完就让回去，手上的目标从原地接着做（它不计时）。几个插一下按下达先后做，最多排 4 个；手上的事 3 秒内腾不出身子（开着车、悬在半空、正在处理急事）、人按 F8 在操作角色、前面已经排满时，以 `WRONG_TIME` 结束，说清是哪一种。它不跨世界，不能 `pause`，要停用 `cancel`；目标查询里手上的目标会说正在等哪件插一下做完。

有的能力按这一次的参数定执行方式：`lookup` 能力列表里的 `mode` 是它最多会怎样。`chat` 写 `controls_player`，公屏说一句话（不给 `target`、`message` 不以 `/` 开头）按插一下跑，不替换手上的目标，角色身体正忙腾不出来时等半秒就不逐字打、整句直接发出（结果细节 `typed=false`）；发游戏命令、对一只生物说话仍替换手上的目标。

**估算**（2026-10-27 批准）：`dry_run` 的回复带 `estimate`，说这件事此刻要花多大功夫：档位 `effort`（`ready` 不用离开 / `nearby` 知道在哪、走过去 / `search` 要出去找 / `blocked` 按这次的写法弄不到 / `unknown` 估不了）、`what`、`how`、`farthest_blocks`、`rough_seconds`，一次要几样时每样一条 `items`。字段与估法见物资规格第 17 节。`sequence` 的 `estimate` 是逐步的 `steps`；下达 `sequence`（不是 dry_run）的回复也带一份，不等附近扫完（按顺序做事规格第 13 节）。估算只给 LLM 看，不拦操作，不当期限，也不改动手时走的路。原料链太长、一次估算问满了价时，没估到的那样原料写"原料链太长，没估完"，档位算 `unknown`。

### 2.4 `goal`

| 参数 | 含义 |
| --- | --- |
| `operation` | `get`、`list`、`pause`、`resume`、`cancel`、`answer`（与 v0 的操作集合相同） |
| `goal_id` | 除 `list` 外都要给：`execute` 返回的目标编号 |
| `answer` | 只在 `operation=answer` 时用：所选回答的编号 |
| `path` | 只在 `operation=get` 时用：结束了的目标结果里折起来的一段（JSON Pointer，照抄 `result.folded` 里的 `path`，例如 `/attempts`、`/details/cells`） |
| `offset` | 只和 `path` 一起用：列表或对象从第几项读起，照抄上一页的 `next_offset`；不给从 0 起 |
| `limit` | 只和 `path` 一起用：这一页最多几项（1..200）；不给按一页约 16000 字装，至少一项 |

改动只有一处：工具描述里不再出现任何能力的特例，问题的选项说明写在问题本身里。

**大块证据按路径读**：`goal` 返回的目标、`events` 带 `goal_id` 附上的目标，结果（第 6.1 节）默认只给 `status`、`summary`、`problem` 和小块事实；大块证据从结果里拿掉，列进 `result.folded`，每块写 `path`、`type`（`list` / `object` / `text` / `value`）、`items`（列表与对象有几项）、`chars`（写成 JSON 多少字）。折起来的是：写成 JSON 超过约 4KB 的 `attempts`（两三条短的照原样留着，没做成时一眼看到为什么）、`details` 里写成 JSON 超过约 4KB 的那几项（折完剩下的小项合起来还超过约 8KB 时整个 `details` 折起来）、其余超过约 4KB 的字段（长的 `changes`、`remaining`、`unconfirmed`）。不是删：`goal(get, goal_id, path)` 读回那一段，返回 `path`、`type`、`value`；列表与对象再带 `total`、`offset`，还有下一页时给 `next_offset`，`next` 照抄就是下一页；读到的那一页里再大的子块照同样的规矩折起来（对象里的直接拿掉、列表里的换成 `{"folded": 路径}` 占位），路径列在这一页的 `folded`。一句文字、一个值整段给，不分页。目标还没结束、路径不对按 `invalid_parameter` 回，说清结果顶层有哪几段。`execute` 当场做完的只读报告是 LLM 要的那份报告本身，照原样整份给。结果留在目标运行表里，按路径读时现算；目标太久以前结束、已经不在表里时报 `unknown_id`。

**暂停与下新目标**：同一时刻只有一个控制角色的主目标。暂停的若是当前主目标，再 `execute` 下达新的控制角色的目标，它按"被新任务替换"结束，之后 `resume` 回"已经结束"；想回头接着做就先 `resume` 它，别另下新目标。重启后恢复成暂停、不是当前主目标的那些不受影响，`resume` 其中一个时它成为主目标，原来的主目标按"被替换"结束。工具描述里写了同样一句。

**死亡恢复**：角色死后循环停摆时，会挂出一条「死亡恢复」决策记录（`ability` 为 `death_recovery`，`goal_id` 是负数），`goal(list)` 与 `goal(get)` 都看得到它（它出现在目标列表里，`ability` 是 `death_recovery`，但不是 LLM 下达的目标），问题带死亡现场的事实（分数、位置）。选项按世界规则给，和死亡界面上的按钮一致：普通世界给 `respawn`（发原版重生请求，成不成由游戏结算），极限模式不能重生，给 `spectate`（旁观这个世界，发的是同一个请求，服务器切成旁观）；连接不在时这两个都不给；`cancel_goal` 永远有，取消当前目标，死亡屏幕留给人处理。用 `goal(answer)` 按选项编号回答；普通世界挂出 2 秒还没人回答，就像真人看一眼死亡界面那样自动点重生（结果写明是自动点的），掉的东西五分钟就消失，等不起；极限模式不自动选；同一个死亡过程只问一次，请求发不出去会重新挂上同一个问题，已消费的问题不再收迟到的重复答复。暂停、恢复、取消对这条记录不适用。

**跨重启**：退出游戏、换世界、崩溃之后，还没做完的目标按世界分开存着；再进同一个世界时全部恢复为 `paused`（`goal(list)` 看得到，并发一条 `paused` 事件），`goal(resume)` 之后才接着做。手上的任务没法跨重启，恢复后能力重新看现场决定；`sequence` 从中断的那一步接着做，前面做完的步骤照样算进成败和变化。同一个世界里编号跨重启只增不减。

### 2.5 `events`

参数：`topic`、`goal_id`、`stream_id`、`after_cursor`、`wait_ms`。语义与 v0 的 attention 相同（游标、重新同步、唤醒原因）：`wait_ms` 内没有新事件就空手返回，有就立刻返回。拆成单独工具，是为了让宿主可以只把它留给自己用。Amaidesu 一侧仍可以把这些事件叫 attention。每次进世界（包括重进同一个世界）事件流换一条新的 `stream_id`，拿旧游标读会得到 `stream_changed`。

每一页的 data 顶层都带 `world`：角色眼下在哪个世界。宿主一直挂着读事件，换存档、退回主菜单不用另外问。

| 字段 | 含义 |
| --- | --- |
| `id` | 世界编号：64 位小写十六进制，不含存档路径或服务器地址原文。同一个存档重进、重启游戏不变；不同存档不同；删了存档用同名文件夹重建（例如又建了一个默认名"新的世界"）、复制出来的存档都是新编号；整个存档搬了位置、服务器换了机器编号照旧。一次进世界期间给出后就不再变。宿主按它把不同世界里记下的事分开，Mod 自己的世界记忆、没做完的目标也按它存（旧版本按存档目录或服务器地址存的，玩过一阵的世界第一次进时整体搬过来，刚建好的世界不搬） |
| `name` | 给人看的名字：单人是存档名，多人是服务器列表里的名字（直连时是游戏给的默认名）；不当键用，存档改名也会变 |
| `source` | 编号从哪来：`world_id_file` 存档自己的世界编号文件（服务端 MaiCraft 写在存档的 `data/maicraft_world_id.dat`，握手时报来；单人游戏的内置服务器也一样）；`server_address` 服务端 MaiCraft 版本太旧、握手没报编号时按服务器地址算，同一地址换了地图认不出来；`save_folder` 单人存档的编号文件写不进去时按存档目录算，删档后同名重建认不出来 |
| `online_mode` | 这个世界所在的服务器开没开正版验证（服务器设置里的 `online-mode`），服务端 MaiCraft 握手时报：`on` 开着，玩家 UUID 跟着正版账号走，改名还是同一个人；`off` 关着（离线模式），玩家 UUID 由名字算出，改名就成了另一个人，冒用别人的名字也认不出来；`unknown` 服务端 MaiCraft 太旧、握手没报。专用服务器照服务器设置报；单人世界与开局域网的主机是本机集成服务端的设置，原版恒为 `on`（来串门的局域网玩家要过正版验证）；连别人开的局域网照那台主机的设置报。按进世界握手时读到的答，这一趟里不变：单人世界进来以后再开局域网、开的时候被模组关掉的正版验证，这里看不到，照旧报 `on`。服务器挂在 Velocity、BungeeCord 这类代理后面时，后端自己关着正版验证、由代理去验，这里照后端的设置报 `off` |

- 不在世界里，或者进了世界、和服务端 MaiCraft 的握手还没回话（还没认出是哪个世界）时，`world` 是 `null`：字段照样在。角色的现场要等认出世界才建，这几刻里 `observe`、`execute`、`goal` 都按不在世界里答，角色不动。
- `world` 一变，正在等事件的读取当场返回，空页也返回，不用等到 `wait_ms`：认出世界（进世界时事件流同时换新，这一页是 `stream_changed`）、退出世界（事件流不换，这一页是 `valid` 的空页，离开前停手的 `paused` 照样读得到）。两条流（`self`、`chat`）都这样。不为此另发事件种类。
- 没装服务端 MaiCraft 的服务器握手不会回话，客户端过一会儿会主动断开，那里 `world` 一直是 `null`。

事件的 `kind` 取小写枚举名：`started`、`asked`、`paused`、`resumed`、`step_finished`、`finished`、`stalled`、`temporary_task_started`、`temporary_task_finished`、`need_unhandled`、`character_died`、`death_recovery_applied`、`gear_broken`、`reminder`、`discovered`、`hurt`、`dimension_changed`、`follow_status`、`sky_changed`、`timer_due`、`others_blocks_broken`、`others_food_taken`、`player_body_language`、`others_things_touched`。`others_things_touched` 是角色从别人放的容器（`whose=player`）里确认取走或存进东西、拆掉或改动了别人放的方块时发出的知情事件（归属不拦动作，自然战利品容器、自家、无记录与归属未问到的不发；饿急了拿别人口粮仍走 `others_food_taken`、卡坑脱困挖别人方块仍走 `others_blocks_broken`，不重发）：手上有正在推进的目标且没被生存需求临时任务借走身体时带 `goal_id` 与当前步骤 `ability`，临时任务动手时不带；一次开箱合在一条里，同一个目标里连着拆同一个人的方块合在一段拆完时发一条；按字段的事实挂在 `others_things` 上：`action`（`took` / `stored` / `broke` / `changed`）、`owner`（在线写名字，不在线写"一位不在线的玩家"）、`owner_uuid`、`block`、`at`（`x`、`y`、`z`、`dimension`）、`items`（仅 `took` 与 `stored` 带，每项 `item`、`count`）、`count`（仅 `broke` 连拆多格时带）。`player_body_language` 是别的玩家冲角色做的肢体动作（与目标无关，不带 `goal_id`）：蹲起、挥手、拿出东西、点头、摇头、原地跳（一段里只跳一下的不报）、扔东西、做完走开又回头。只认 16 格内看得见的别的玩家，一段里至少有一下是看着角色做的、挥向角色的或扔到角色身边的才发，他对着别人蹲、自己在挖矿不发。同一个人 1.5 秒没有新动作就把这一段发出去，一直在做的每 6 秒一条，几个人各记各的；扔出的东西还在飞、他做完正走开时等一等，回头了一起说。消息一句话按先后写谁（玩家名，看得见带观察编号）、做了什么、几下、对着谁或哪儿、拿着什么，最后写他在角色哪个方位几格、此刻看没看着角色，例如"玩家 Alex（e4）看着你蹲起 4 下，拿出铁剑，对着你挥了 2 下；他在你前方 3 格""玩家 Alex（e4）朝你扔了 3 个面包（e9），落在你左侧 1 格；他在你左前方 2 格""玩家 Alex（e4）看着你蹲起 2 下，往北走了 6 格，又回头看着你；他在你前方 7 格"。另带结构化字段 `player`：`name`、`uuid`、`id`（看得见时的观察编号），宿主按它把事件和身边的人对上，不用解析句子。同一个人一分钟超过 12 条时，这一分钟剩下的合成一条写总数（"这一分钟又蹲起 40 下、挥手 12 下"）。客户端看不到的照实不报：他右键角色、在打字、开着什么界面、表情动画类模组的动作。这些动作在玩家之间多半是什么意思、怎么回，见随包技能 `social/player-body-language`。带 `goal_id` 的目标事件（`started`、`resumed`、`paused`、`asked`、`stalled`、`finished`、`step_finished`）另带 `ability`：这条事件说的是哪个能力，和 `execute` 时传的一样；sequence 的一步的事件记在整件 sequence 的 `goal_id` 上，`ability` 写那一步的能力，整件 sequence 开始、结束时写 `maicraft:sequence`。消息文字不变，宿主认能力看这个字段，不解析消息开头；死亡恢复决策的提问与结果、与目标无关的事件不带。`others_food_taken` 是饿到饱食度 6 及以下（不能疾跑）、身上和附近的箱子里都没口粮，从不是角色自己放的箱子里拿了刚好够吃回线以上的现成口粮（与目标无关，不带 `goal_id`）：每确认拿到一次发一条，拿了没确认进背包的不发；消息例如"饿到饱食度 3，从 Alex 家的箱子（12, 64, -8）拿了 1 个面包"，按字段的事实在事件的 `others_food_taken`：`whose`（`player` 归属记录上的人 / `unknown` 归属还没问到）、`owner`（只在 `player` 时有，在线写名字、不在线写编号）、`at`（`x`、`y`、`z`、`dimension`）、`items`（每样 `item`、`count`）、`food`（拿之前的饱食度，和 `observe(self)` 的 `food` 同一个数）、`losing_health`；那次吃饭临时任务结束时的 `temporary_task_finished` 消息末尾也带一句从谁家的箱子拿了什么。只拿面包、熟肉、熟鱼、蔬菜、水果这类现成的普通口粮，生肉生鱼不拿；额外保护的地标旁、记住的区域里的箱子不拿。`others_blocks_broken` 是角色被方块封死在小坑里、卡坑脱困挖开了别人放的普通方块：那次脱困一收场（出了坑或走不通）当场发一条，消息写在哪被封住、挖了谁的几格、出没出来；逐格的明细在出行结果细节的 `others_blocks_broken`（`at`、`block`、`placed_by`），`changes` 里每格一条 `block_broken`，说明写是谁放的。`step_finished` 是 `sequence` 里的一步做完了，记在整件 `sequence` 的 `goal_id` 上，消息是"第几步（能力，目的）：这一步的结论"，例如"第 3 步（maicraft:build，砌东墙）：按图建好了"，没写目的时括号里只有能力。`stalled` 是一条还没结束的目标太久没有任何新事件（与目标无关的事件不算）：带它的 `goal_id`，消息写目标编号、目的与多久没动静，同一个停滞只提醒一次，目标有了新事件或结束就重新计时；受理方不必自己拿表计时等终态。`finished` 与 `step_finished` 另带 `self_brief`：结束那一刻角色的一行自身摘要，在哪（含维度）、血（和 `observe(self)` 的 `health` 同一个数，整数照写，带小数写一位）、饱食、在水里时的氧气、手上拿着什么（副手另有东西一并写）、开着什么界面与谁开的，例如"在 minecraft:overworld 12, 64, -8；血 18，饱食 15；手上 minecraft:iron_pickaxe；开着储物界面（minecraft:generic_9x3，任务点开的）"；不附背包，背包看 `observe(self)`；结束时读不到角色（刚进世界）就不带这个字段。`step_finished` 还可能带 `ready_now`（2026-10-27 批准）：这件 `sequence` 后面还没开始的步骤里，此刻档位是 `ready`、不用走路就能做的那几步，每条 `step`、`ability`、`purpose`、`how`，消息末尾也说一句；一条都没有就不带（按顺序做事规格第 13 节）。`temporary_task_started`、`temporary_task_finished`、`need_unhandled` 与目标无关，事件里不带 `goal_id`：临时任务的开始与结束是生存需求自己派活（自卫、回洞、退开）与收工；`need_unhandled` 是角色自己处理不了的生存需求（饿了、弄不到吃的这类），主任务不受影响，照常推进。`character_died` 也与目标无关、不带 `goal_id`：角色血量见底进了死亡流程，只发这一条，循环停摆等重生，重生后从原地接着做。死亡恢复决策的提问走 `asked`、执行结果走 `death_recovery_applied`，都带决策记录自己的负数 `goal_id`，`goal(answer)` 回答它；`events` 按这个 `goal_id` 读，只拿到这条决策的提问和结果。`reminder` 是角色身上要 LLM 知道的事出现与撤下。`discovered` 是探索途中看见了值得记下的东西（群系、岩浆湖、结构线索、留意清单上的方块或实体）：一句话带发现是什么与方位距离，同一条发现只发一条；角色不因发现停下、不问，想改主意随时暂停或取消，完整的发现清单在探索结果里。`hurt` 是刚才挨了一阵打（与目标无关，不带 `goal_id`）：同一个来源（同一个攻击者，没有攻击者时同一种伤害，例如摔落、溺水、着火）连着挨的算一段，不分开始和结束，一段只发一条——5 秒没再挨这个来源的打就发；一直挨着打不停时每 10 秒发一条，只算这 10 秒里的。消息一句话写清谁打的（玩家写玩家名，有名字写名字，看得见带观察编号）、什么伤、几下、掉了多少、还剩多少，例如"被骷髅（e3）射中 3 下，掉了 6 点血，还剩 8 点"；没收到伤害包、只看到血掉了的写明"只看到血掉了"；黄心（伤害吸收）到期掉的不算。认得出是谁打的段另在事件上直接铺攻击者字段：`attacker`（攻击者实体类型 ID，例如 minecraft:skeleton、minecraft:player）、`attacker_name`（干净名字，不带观察编号后缀）、`attacker_entity_id`（游戏实体编号），宿主按字段认攻击者，不解析句子；没有攻击者的伤、只看到血掉了的不带。被别的玩家打中分两种：拍一下（10 秒内打中不到 3 下、或累计掉血不到 6 点，又没掉到拒战线下；雪球、鸡蛋这类不掉血的也算）不进 `hurt`，当刻在 `player_body_language` 里说一次（"拍了你一下：空手，没伤到"），角色不退开、不停工；PvP 关着、没打出伤害时，他对着够得着的角色挥手也算拍一下。连打（10 秒内同一人打中至少 3 下且累计掉了至少 6 点，或打到拒战线下；箭、三叉戟这类掉血的投射物一律算）从变成连打的那一下起进 `hurt`，前面几下已经当拍一下报过、不重报；陌生玩家连打时角色退到他够不着的地方、举盾、不还手，他停手后暂停主任务发 `need_unhandled` 等你决定，自家人连打只发 `hurt`。同一下伤害只出现在一条事件里；角色死了时没发出的那段丢掉（`character_died` 已经说了），换世界、断线时也丢掉。`dimension_changed` 是换了维度（与目标无关）：从哪到哪、落在哪，例如"从主世界到了下界，落在 12, 70, -8"，走门过去、重生到另一个维度都算。`sky_changed` 是天色变了（与目标无关，不带 `goal_id`）：天黑（到了能睡的时间）、天亮（过了能睡的时间）、开始下雨、雨停，只在变的那一刻发一条，括号里带此刻的时间与天气，例如"天黑了，到了能睡的时间（夜晚，距天亮约 9 分钟；晴）""开始下雨了（白天；雨）"；白天打雷把天压暗到能睡时写"雷暴把天压暗了"，雷暴过去写"雷暴过去，天又亮了"。能不能睡和夜晚生存需求用的是同一个判断，所以下雨天天黑得早一点。没有昼夜的维度（下界、末地）不发；刚进世界、刚换维度两秒内只记下当下，不算变。人自己玩的时候也照样发。`follow_status` 是跟随中的处境变化（与目标无关，不带 `goal_id`；同一时刻只有一个跟随在跑）：跟不过去停下等、又跟上了、跟丢了在找（分过门、死了、下线、走远）、找回来了、跟着过了传送门、坐上或没坐上他那辆、下车、开始与结束帮他打，一句话写清发生了什么、他在哪、我在哪；跟不过去时还写放开哪项许可也许能过去。跟的是玩家时另带结构化字段 `player`：`name`（玩家名）、`uuid`，和 `player_body_language` 的 `player` 同一个写法（不带观察编号），宿主按 `uuid` 认出跟的是谁，点名时用的是观察编号也对得上；跟的是动物、女仆这类时不带。角色不因这条停下等回答，想改主意随时取消或换许可重下。`timer_due` 是 LLM 用 `timer` 设的计时到点了（与目标无关，不带 `goal_id`）：消息带计时编号、设时写的备注、设了多少秒和到点时的游戏时间（说法和 `observe` 里的 `time` 一样），例如"计时 3 到点：看炉子烧好没（600 秒前设的；此刻白天）"；另在事件上直接带 `timer_id`（计时编号，和 `timer` 结果、`obtain` 结果细节 `left_cooking` 里的 `timer_id` 是同一个数）与 `note`（设时写的备注，原样），宿主按 `timer_id` 认是哪个计时，不解析消息，例如 `{"cursor": 12, "kind": "timer_due", "message": "计时 3 到点：…", "timer_id": 3, "note": "回 (12, 64, -30) 的熔炉取干海带 ×64"}`；`obtain` 装好炉先走时自动挂的回炉计时到点也是这一条；计时不占身体，角色这期间照常干别的；按游戏时间计，单人游戏暂停时不走；换世界、断线时没到点的清掉，不发。

`topic` 选读哪条流：`self`（默认）是上面这些角色身上发生的事（和 `observe(what="self")` 对应：`observe` 看角色现在怎样，`events` 看角色身上发生了什么）；`chat` 是聊天栏收到的消息。两条流各有自己的 `stream_id`、游标和保留条数（各留最近 256 条），游标、等待与重新同步的语义相同；`goal_id` 只在 `topic=self` 时用，带上时还附上这个目标此刻的样子（`goal`）。聊天单独一条流，是为了服务器上有人刷屏时不把目标的事件挤掉。

`topic=chat` 每条事件的字段：

| 字段 | 含义 |
| --- | --- |
| `cursor` | 序号 |
| `kind` | `player` 玩家说的话；`system` 服务器的系统消息（进出、死亡播报、公告、命令反馈……，以及借角色名字代发的消息） |
| `sender` | 发言人名字；系统消息没有，名字还没同步到时也可能没有 |
| `sender_id` | 发言人 UUID；同上 |
| `sender_online` | 只在 `player` 上有，总是写：发言人是不是此刻在线玩家列表里的那个玩家，Mod 收到时核对过。有发言人 UUID 的，按 UUID 在玩家列表里查到、名字也对得上才是 `true`（签没签名都一样）；没签名的服务器转来的公屏聊天，名字在玩家列表里就是 `true`；控制台、命令方块的 `/say` 这类没有发言人 UUID、只借了个名字的是 `false`。`system` 没有发言人，不写 |
| `shown_as` | 借角色名字代发的消息才有：聊天格式里写的那个名字（就是角色自己的显示名） |
| `text` | 原话；借名代发的去掉聊天格式加的"<名字> " |
| `private` | 别人私聊角色（`/msg`）时为 `true`，其余不出现 |
| `truncated` | 原话超过 1024 字、后面被截掉时为 `true`，其余不出现 |
| `mentions` | 消息里点到的实体，按出现先后，每只 `name`（文字里显示的名字）、`type`（实体类型 ID；只认得出 UUID 时没有）、`uuid`；同一只只列一次，一只都没有时不出现 |
| `translation_key` | 消息整句是一条游戏翻译时的翻译键，例如 `death.attack.explosion.player`；不是时不出现 |

- 角色自己说的话（发言人 UUID 是自己）和动作栏提示不进这条流。
- 没有签名聊天的服务器把玩家的公屏聊天整句当系统消息发下来，格式仍是公屏聊天那一条（翻译键 `chat.type.text`，"<名字> 原话"）。名字在当前玩家列表里的，按那个玩家说的话记：`kind` 为 `player`，`sender` 是名字，`sender_online` 为 `true`，没有 `sender_id`（拿不到发言人凭据），`text` 是不带"<名字> "的原话，不带 `translation_key`；名字是角色自己的（和账号名一样，或名字点着的实体是角色）是自己说话的回显，不进这条流。名字不在玩家列表里的照旧按 `system` 记。例如 `{"kind": "player", "sender": "Alex", "sender_online": true, "text": "不是我的"}`。
- 借角色名字代发的消息：没有发言人 UUID（服务器或模组用系统消息伪装成的聊天），聊天格式里写的却是角色自己——名字点着的实体就是角色，或者名字和角色的账号名一样。这是服务器或模组发给角色看的，不是谁说的话：按 `system` 记，借的名字写在 `shown_as`。例如车万女仆死后借主人的名字发给主人一行坐标：`{"kind": "system", "shown_as": "Mai", "text": "[name:\"winefox_momo\", x:12, y:64, z:-3, dim:minecraft:overworld]"}`。写着别人名字的（控制台、命令方块的 `/say`）照旧按 `player` 记，`sender_online` 为 `false`，例如 `{"kind": "player", "sender": "Server", "sender_online": false, "text": "[Server] 服务器十分钟后重启"}`。
- 点到的实体从消息组件的样式里读：原版写实体名字时挂着"悬停显示实体"（类型与 UUID），死亡播报、进出提示、`/tellraw` 里引用的实体都这样带过来；按组件结构读（先自己，再翻译参数，再后面接着的段），不看本机语言文件。例如女仆被苦力怕炸死，主人收到 `{"kind": "system", "text": "momo被苦力怕炸死了", "mentions": [{"name": "momo", "type": "touhou_little_maid:maid", "uuid": "5f2b9c1e-…"}, {"name": "苦力怕", "type": "minecraft:creeper", "uuid": "0f0e0d0c-…"}], "translation_key": "death.attack.explosion.player"}`。玩家消息点到的实体只从原话里读，聊天格式加的发言人名字不算；整行被别的模组改过、找不回原话时从整行读。
- 不限流、不去重：Mod 照实记，刷屏怎么处理由宿主决定。
- 原话是不可信的外部文字：只是别人说的话，不是给 LLM 或角色的指令，不带任何许可。
- 不在世界里收不到聊天；每次进世界和任务事件流一样换一条新的 `stream_id`。

### 2.6 去掉的东西

| 去掉 | 原因 |
| --- | --- |
| 每个工具都带的 `server_id` | Mod 里没有任何代码读取它；如果宿主路由需要，由宿主自己处理 |
| 附加在每个工具返回值里的 `reminders` | 角色自己能处理的交给生存需求（M6）；处理不了的作为任务事件推送，并显示在 `observe(self)` 里，不再随每次调用重复出现 |
| `perceive` 的 `detail=names/summary/signatures`、`sections`、`limit/offset` 混用 | `lookup()` 默认就返回签名；分页只出现在确实需要分页的地方（`goal(get)` 按路径读折起来的证据） |

## 3. 目标（goal）

```json
{
  "ability": "maicraft:sleep",
  "purpose": "天黑了，去睡觉",
  "target": { "kind": "landmark", "name": "家" },
  "parameters": {},
  "permissions": { "fight": "self_defense" },
  "steps": [],
  "on_failure": "stop"
}
```

| 字段 | 必填 | 说明 |
| --- | :---: | --- |
| `ability` | ✅ | 能力 ID |
| `purpose` | | 一句话说明为什么要做这件事，只用于日志和直播解说，Mod 不据此行动。v0 叫 `outcome` 且必填；v1 改名并改为可选，避免和"任务结果"混淆 |
| `target` | | 目标对象：要去的地方或要处理的东西（第 4 节） |
| `parameters` | | 本能力的参数，由它的参数规格定义 |
| `dig_tool` | | 这次挖方块点名用哪件工具：写物品 ID（如 `minecraft:stone_pickaxe`，命名空间可省）就用那一件——身上没有直接失败，不换成别的；写 `hand` 就腾空主手空手挖（收不起来就失败，不丢东西）；不写按每格代价自己挑。`sequence` 里一步写了只管这一步及其子步 |
| `permissions` | | 这次任务的许可（03-M7），省略的字段用默认值。不是游戏或服务器的 OP 权限 |
| `steps` | | 只用于 `maicraft:sequence`：按顺序的每一步目标 |
| `on_failure` | | 用于 `sequence` 里的一步：这一步失败后 `stop`（整件事停下）还是 `continue`；写在 `sequence` 本身上时，当作每一步没单独写时的默认 |

`permissions` 的字段：

| 字段 | 取值（默认值加粗） | 含义 |
| --- | --- | --- |
| `change_blocks` | `none` / `temporary` / **`natural`** / `any` | 能改变哪些方块：不改 / 只搭临时方块并收回 / 放行改变自己放的之外的不受保护方块（天然取材仍只挑天然地形，收回只挑自己用过的台子与床；圈地与保护地标另挡，谁放的只作事实与事件回报） / 一切不受保护的方块 |
| `fight` | `self_defense` / **`hostile_mobs`** / `any` | 只自卫 / 主动处理敌对生物 / 可以攻击指定的任何目标 |
| `use_rare_items` | **`false`** / `true` | 能否用末影珍珠、不死图腾、钻石这类稀有消耗品；目标本身就要用的不受它管（去末地插的末影之眼、过折跃门扔的末影珍珠照用） |
| `kill_animals` | `none` / **`wild`** / `any` | 能否为了具体需要击杀动物（剪毛、挤奶不算） |
| `survival_needs` | **`on`** / `off` | `off` 时本目标执行期间吃饭、睡觉、补光这类起居需求不再插队，角色能连着把一件事干完；被攻击照样自卫、溺水照样换气、快摔死照样护住落地。寻死这类任务自己声明关掉时才是一个生存需求都不插 |
| `protected_landmarks` | 地标名列表 | 额外不许碰的地方 |

**删除 `preferences` 和 `constraints`**：v0 里没有任何一个能力接受它们（所有声明都是空的），却要求每次调用都带上这两个空字段。

## 4. 目标对象（target）

全接口只有这一种"指一个地方或一个东西"的方式：

| kind | 字段 | 含义 | 取代 v0 |
| --- | --- | --- | --- |
| `here` | — | 角色当前的位置；`travel` 里指脚下这一带头顶见天的地面（在地下就走出去或挖楼梯上去） | `current_place` |
| `seen` | `id` | 观察时看到的东西：`e#` 实体、`f#` 地形特征、`b#` 方块或设施 | `entity`、`nearest` 的大部分用法 |
| `landmark` | `name` | 地点名：记住的地点优先；没记过时认附近看得见、写着这个名字的那块告示牌，落在牌子那一格。比的是"相同"不是"包含"（只留字母、数字、汉字，不分大小写；牌子一面里某一行，或整面连起来）；几块同名的牌子挨在一起（3 格内）算一处取最近的，隔得开就不挑、列出编号让你用 `seen` 指。保护名单与施工、读现场只认记住的地点 | `landmark`、`area` |
| `position` | `x`、`z`，可选 `y`、`dimension` | 坐标；**`y` 可以省略**，到了附近再找能站的高度（M10）；带 `dimension`（命名空间维度 id）就是"那个维度的这个坐标"，坐标按目标维度自己的坐标系写 | `coordinates`，以及 `travel` 的 `parameters.destination` 特例 |
| `dimension` | `name` | 就是去那个维度：`name` 写命名空间维度 id，例如 `minecraft:the_nether` | 新增 |
| `player` | `name` | 一位玩家 | `player` |
| `direction` | `toward`、`distance` | 朝某个方向走多远：`toward` 取 `forward` / `backward` / `left` / `right` / `north` / `south` / `east` / `west`，例如"往北 100 格" | 新增 |
| `previous` | 可选 `step` | 前面某一步确认过的位置 | `prior_result` |

- "某片区域"等于任意目标对象加上 `parameters.radius`。
- "最近的某种东西"不再是一种目标对象：要么先 `observe` 拿到观察编号再用 `seen`，要么由能力自己按参数去找最近的（例如 `use` 一台熔炉时只给 `block`）。
- 观察编号对应的东西不在了（实体走远、方块被拆）时，能力以问题 `TARGET_GONE` 结束，并说明最后一次看到它的方位。
- 观察编号短期有效：实体离开视线约 10 秒、设施与地形特征约 2 分钟后失效。目标在推进时（含 `sequence` 一步接一步地做、在等回答）不按时间失效，只要东西还在：实体还在这个世界里，设施那一格还是那种方块；离得远没加载的设施和地形特征照留。留也有边：离最后一次看见超过 20 分钟的照常失效，到期还留着的最多 256 条，多出来的从最早看见的开始失效。目标被暂停或做完后照常按时间失效。

- 单位用人能直接理解的：格、秒、件。
- 新能力**只能**使用参数名表里的名字；确实需要新概念时，先加进参数名表（代码里是 `ParamNames`），再在能力里使用。
- 宽松写法（`"6"` → `6`、`"true"` → `true`、参数放错一层、对象或数组参数整段写成 JSON 字符串、数组被包成 `{"item": …}`、正文数组里的整数写成字符串）只由 MCP 入口统一处理，并在返回的 `notes` 里说明做过哪些规范化。有的模型调工具时会把参数里没写结构的数组包成只有一个 `item` 键的对象（嵌套在正文里的也包，例如 `cells` 每格的 `offset`），数组里的整数还会变成字符串：值是数组的 `{"item": […]}` 在哪一层都取出数组照收；值是单个对象的 `{"item": {…}}` 只在参数本身声明了要数组时当一项的数组收（正文里面不知道该是什么形状，不猜）；正文里全是数字的数组中写成字符串的整数（`["0","1","0"]`）换回整数，混着文字或小数的数组不动；期望对象的参数本身不拆。每种修法在 `notes` 里各说一次。别的写坏的地方，把正文整段写成字符串仍是能原样传到的办法；字符串读不成 JSON 时，错误里写明坏在第几行第几列。

## 6. 返回格式与错误

所有工具返回同一个结构：

```json
{
  "ok": true,
  "data": { },
  "notes": ["parameters.count: \"6\" 按整数 6 处理"],
  "next": { "tool": "events", "arguments": { "goal_id": "…", "stream_id": "…", "after_cursor": 42, "wait_ms": 30000 } }
}
```

失败时：

```json
{
  "ok": false,
  "error": {
    "code": "invalid_parameter",
    "message": "参数有 2 处问题",
    "fields": [
      { "field": "goal.parameters.count", "message": "count 必须是整数", "expected": "integer 1..256", "received": "文字 \"很多\"" },
      { "field": "goal.parameters.item", "message": "没有叫 minecraft:torches 的物品", "expected": "物品 ID 或 # 开头的标签" }
    ],
    "example": { "ability": "maicraft:obtain", "parameters": { "item": "minecraft:torch", "count": 8 } }
  }
}
```

- `error.code` 是一个小而稳定的枚举：`invalid_parameter`、`unknown_ability`（附相近能力建议；能力需要的模组没装时，写明缺哪个模组；写的是删掉的能力名，例如 `wait`，直接说改用什么）、`unknown_id`（观察编号、目标编号、计划编号或资料地址不存在）、`not_in_world`、`busy`（客户端线程迟迟没轮到，同时在做的联网查询满了，或上一张画面正在拍、离上一张不到 1 秒）、`unavailable`（要的东西这一次拿不到：联网查询关着、连不上、超时、站点不让读或读不出，或游戏这一秒没画出新的一帧画面；不说明那样东西不存在）、`too_large`（算出来的回答比单次上限还大，这次整体不返回数据，把查询收窄再试）、`internal_error`。
- 校验错误一次报全，而不是改一个错报下一个：每一处写错的地方是 `error.fields` 里的一项（`field`、`message`，能说清时带 `expected`；形状不对时带 `received`：收到的是什么类型加一小段原文，例如 `对象 {"item":[…]}`、`文字 "here"`）；不是参数问题时没有 `fields`。`execute` 的参数表里 `goal` 写全了结构：每个字段、`target` 的几种写法、许可的取值。
- 任务的结果走第 6.1 节的任务结果，不放进错误：**工具调用成功、任务失败**是两回事。
- MCP 调用结果的 `content` 里，上面这段 JSON 是一个文字块。`observe(what="picture")` 成功时在它后面多一个图片块（`type=image`、`mimeType=image/jpeg`、`data` 是 base64）；图的字节不进 JSON。不认图片的宿主照样读得到文字那一块。

### 6.1 任务结果

所有能力用同一个结构告诉 LLM 做得怎样（代码里是 `TaskResult`，设计见 03-M8）：

```json
{
  "status": "partial",
  "summary": "床备好了，现在是白天睡不了",
  "changes": [ { "kind": "item_gained", "what": "minecraft:white_bed", "count": 1 } ],
  "remaining": ["入睡"],
  "problem": { "kind": "WRONG_TIME", "message": "现在是白天", "suggestion": "约 5 分钟后天黑" },
  "unconfirmed": [],
  "attempts": [ { "tried": "从门口那一侧靠近床", "result": "被墙挡住，看不见床头" } ],
  "details": { "bed_source": "crafted" }
}
```

| 字段 | 含义 |
| --- | --- |
| `status` | 目标达成情况：`done` / `partial` / `failed` / `cancelled` |
| `summary` | 一句话结论，可以直接用于直播解说；失败时只写卡住的那一句结论，展开的原因在 `problem.message`。结束事件的 `message` 就是这一句 |
| `changes` | 已确认发生的变化（动了调用方预留的那几条带 `from_reserved`：其中几件是预留的，预留已跟着扣掉）：`item_gained` 拿到、`item_consumed` 用掉、`item_stored` 存进、`item_dropped` 丢掉的物品，`block_placed` 放下、`block_broken` 拆掉的方块，`block_changed` 方块还是那一格但状态或种类变了（门开了、锄成了耕地、火点着了），`entity_affected` 打到或击败的生物，`moved` 移动 |
| `remaining` | 没完成的部分 |
| `problem` | 卡在哪：`kind`（下表）、`message`（用游戏里的话说清楚：先一句结论，展开用"；"接在后面；备料一层层没拿到时，最外层把各层没拿到的东西摊平讲一次，同一样东西只讲一次，卡在同一处的几样合成一组并写明几样；`build` 有几格没做成时，同样的原因合并计数写进结论句，格数多的原因在前，最多点名两种、其余写还有几种原因共几格，`kind` 跟着格数最多的那种原因：站位、视线、走不到、没加载是 `UNREACHABLE`，修了几轮还不对、点了不生效、生物一直挡着、结果没能确认是 `STUCK`，基岩这类按游戏规则挖不动是 `NOT_POSSIBLE_HERE`，施工调不了的点名属性、挖掘没接上才是 `UNSUPPORTED`；受保护的格与缺料照旧先问 `NEED_APPROVAL`、`NEED_ITEM`；`machine_build` 普通格交施工做的部分照施工的问题转述，施工做全了而安装段、部件、设置有没做成的，同样按原因合并计数写进结论句，`kind` 跟着件数最多的那种原因（动作自己的失败照它的种类，宿主没加载是 `UNREACHABLE`，动作做完了核对没装上是 `STUCK`，没有机器类型认、结构上还不会才是 `UNSUPPORTED`，这时才提示装上联动再来）、`suggestion`（怎样能继续；没把握时不给） |
| `unconfirmed` | 已提交、但没能确认结果的交互；这些不能盲目重做。一笔一条，`note` 写明点的是什么、当时看到什么 |
| `attempts` | 试过的办法摘要 |
| `details` | 能力特有的细节，每个能力在自己的能力说明里列出 |

问题种类（`problem.kind`）：

| 种类 | 意思 |
| --- | --- |
| `INVALID_PARAMETER` | 参数不对，不进世界就能发现：物品或方块 ID 不存在、标签下一件注册物品都没有，或缺了必填的、取值超了范围、几个参数凑不到一起 |
| `NEED_ITEM` | 缺东西（材料、食物、床、够格的工具），而且自己弄不到 |
| `NEED_APPROVAL` | 要做的事超出这次任务的许可，需要 LLM 同意；通常伴随一个提问 |
| `UNREACHABLE` | 到不了：试过的站位和路线都不通 |
| `NOT_FOUND` | 没找到：观察编号或名字对不上任何东西，或查过的范围里没有（查了多大范围随问题写明）；"曾经见过、后来没了"用 `TARGET_GONE` |
| `TARGET_GONE` | 目标对象没了 |
| `DANGER` | 继续下去会死，或大概率重伤 |
| `REFUSED_BY_GAME` | 游戏或模组拒绝了这次交互（包括服务器的领地保护、权限不够），附上游戏给的原因 |
| `WRONG_TIME` | 时间不对，例如白天不能睡 |
| `NOT_POSSIBLE_HERE` | 在这里按游戏规则就做不到，例如下界用床会爆炸 |
| `INVENTORY_FULL` | 背包塞满，能搬的都搬了（合并散堆、随身背包、存箱子存网络）还是腾不出空位；建议里照现场列出可丢的候选、记得的容器与 `drop`、`deposit` 能力名，处置后重新下达 |
| `STUCK` | 卡住了：换过办法仍长时间没有真实进展，或超过了最多能做的时长 |
| `UNSUPPORTED` | 目前不支持这件事，或需要的模组没装 |
| `INTERNAL_ERROR` | 程序出错，不是游戏里发生的事 |

`suggestion` 永远有：任务层写了有把握的建议就用它；没写时按种类给一句通用的下一步（卡住了换办法、不支持换途径并说明不是 MCP 坏了、程序出错换个目标接着玩并告诉主播……）。太多限制与没有下一步的报错会让小模型以为 MCP 坏了。

## 7. 观察视图（`observe`）

### 7.1 `observe(what="scene")`


- `summary` 是一句话总览：列出了几个实体（几只敌对、几只盯着角色）、几处设施与地形、远处只计数的有几只。每一条的方位、距离、编号只在下面的结构化列表里出现一次，速写不逐条复述（原先同一份内容写两遍，加上一百多格外的蝙蝠、鱿鱼全列，一次观察近三万字）。
- `entities`：盯着角色的、有名字的、玩家、看得见的敌对生物不论远近逐只列（远处看不见的敌对生物只计数）；其他实体（含掉落物）只列 32 格以内。再远的在 `distant_entities` 里按种类报只数，不是悄悄删掉；要找哪一种用 `find`。掉落物的 `traits` 带 `物品` 与 `数量`。活体生物带血量快照：`health` 是当前值、`max_health` 是上限，一格血是半颗心（角色满血 20，末影龙满血 200）；不是活体的没有这两个字段。可驯服的生物（狼、猫、马、女仆）被驯服了时 `traits` 带 `驯服`：`你的` / `自家人的` / `别人的`；自家人的、别人的再带 `驯服者`：驯服它的玩家名（不在线、还没同步到玩家列表时写他的 UUID）；坐下了带 `坐着`。别的玩家按着潜行、蹲着时 `traits` 带 `蹲着`，视线离角色身体不到 1 格时带 `看着你`；玩家的 `name` 始终给玩家的游戏名（和玩家列表、聊天里的名字一致），其他实体的 `name` 只在有名字牌或自定义名时出现。认得出是哪一个的带 `uuid`（游戏给它的 UUID）：玩家、有名字的、被驯服的（谁驯服的都算）；野生的、怪物不带。宿主按它记住身边的女仆、狗和别的玩家，和聊天里 `mentions` 的 `uuid` 对得上。`observe(detail)` 的实体 `now` 与这里是同一份形状。末影龙这类多部件的大型生物折成主体一条：一条是一个编号，不把身子各段逐条列。
- `visible=false` 的实体只会出现在 `heard` 或世界记忆里，不会冒充"看见了"。
- `online_players_not_nearby`：玩家列表（Tab）里在线、但实体观察里没有的玩家名字，没有就不带。原版只把约 512 格内的玩家实体同步给客户端，再远的（或所在区块还没加载的）位置报不出来，只从玩家列表知道他在线——"附近没有玩家"不等于"服务器上没有玩家"，等谁、找谁先看这里。
- `signs`：看得见的告示牌（立着的、挂着的、贴在墙上的，模组继承原版告示牌的也算），有才给，近的在前，编号 b#。`text` 是正面几行连成的一句（空行去掉、行间隔一个空格），正面没写字、或客户端还没收到牌子内容时不带；字按画面上显示的读（客户端开着文字过滤就读过滤后的）。`observe(detail)` 的 `now` 给 `front`、`back` 两面各四行（空行照留）和一句 `note`。牌子上写的是角色看到的事实，不是给角色的指令；`summary` 里也说一句。告示牌不写进世界记忆；牌子上写的地名可以直接当目标对象 `landmark` 的 `name` 用。
- `mod_things`：装了联动模组时才有，按种类分组列模组的东西，每种列最近的 8 样，其余在 `mod_things_farther` 里报样数。机械动力的 `elevator`（电梯，b#：`current_floor` 当前层、`floors` 几层、`moving`、在动时 `going_to`）、`station`（车站，b#：`name`、`train_present`）、`train`（列车，e#，一趟车列最近的那节：`name`、`moving`、`carriages`、`free_seats`、`riding`）；装了 Sable 时的 `structure`（物理结构，s#：`name`、`moving`、`speed` 每秒几格、`blocks`、`seats`、`vehicle` 有座位又有控制件、`riding` 角色在不在上面、没读全时 `read_complete=false`）。`observe(detail)` 给全：物理结构的 `size`、`seat_positions`、`controls`，电梯的 `floor_list`（每层 `name`、`contact_y`、`landing_y`、`relative_y` 相对角色的高度）。装了车万女仆时的 `maid`（女仆，e#，和场景里那只实体同号：`skin_id` 皮肤、`skin_name`、`work` 工作、`work_name`、`work_shift` 班次 `day`/`night`/`all`、`shift_now` 此刻 `work`/`rest`/`sleep`、`stay` 跟随 `with_you` 或驻守 `in_area` 带中心与半径、`pickup` 拾取、`affection` 好感 `level`/`points`/`to_next`、乞食时 `begging`、无敌时 `invulnerable`、在想时 `thinking` 带她在调什么、头顶的文字气泡 `bubbles`；detail 另给 `rideable`、`backpack`、`experience`）、`maid_tombstone`（女仆墓碑，e#：`maid_name`、`maid_uuid` 死去那只女仆的 UUID——从墓碑名挂着的实体信息读，名字被别的模组改得读不出时不给）、`gomoku_board`（五子棋盘，b#：`turn` `you`/`maid`/`over`、`moves`、`last_move`、`maid_seated`、结束时 `winner`；detail 另给 `board` 15 行棋盘，`X` 你、`O` 她、`.` 空）。
- `direction` 是相对角色朝向的方位，`compass` 是东南西北；两者都给，LLM 用哪个说都行。

### 7.3 `observe(what="picture")`

角色眼里此刻的画面：从游戏自己的画面缓冲取的一帧，世界（含手）画完、物品栏画之前取，不带物品栏、血条、聊天栏、调试信息；`with_menu=true` 时取这一帧整个画完的样子，连开着的界面一起。图长边 1280 像素、按窗口的宽高比，JPEG 质量 85，跟在文字那一块后面（第 6 节）。画面只给 LLM 看外观和找东西，数量、血量、背包、聊天、告示牌的字以 `self`、`scene`、`detail`、`events` 为准。

```json
{
  "picture": { "width": 1280, "height": 720, "format": "image/jpeg", "labeled": true, "menu_included": false },
  "camera": { "direction": "前方偏右", "compass": "东北", "pitch": "略向下", "first_person": true },
  "toward": { "id": "小木屋", "turned": true, "framed": "partly", "step_back_blocks": 6 },
  "in_picture": [
    { "id": "e4", "type": "minecraft:player", "name": "Alex", "at": [902, 410], "labeled": true },
    { "id": "b5", "block": "minecraft:chest", "at": [214, 560], "labeled": true },
    { "id": "e9", "type": "minecraft:item", "at": [930, 600], "labeled": false, "not_labeled_because": "太挤" }
  ],
  "menu_open": "storage",
  "summary": "转过去看 小木屋，只拍到一部分，往后退约 6 格能装下；画面里看得见 3 个编号，标了 2 个；开着界面（storage），没拍进去；要连界面一起拍用 with_menu=true。"
}
```

- 转不转头：给了 `id`、角色闲着或主目标在等回答、被暂停时，先转头看过去（读后看的速度，最多等 2 秒），拍完停 0.8 秒再慢慢转回站定朝向；实例配置 `idleLooking` 关着也转。手上有活、生存需求的临时任务占着身体、人按 F8 拿着角色（或进世界以后还没下过目标、控制权还没交给自动化）、骑着坐着飞着睡着、屏幕上开着别人的界面时不转，照镜头此刻拍。没给 `id` 时，闲时看正转头看着别处就先转回站定朝向再拍。
- `picture`：图的宽高与格式；`labeled` 图上标没标编号；`menu_included` 界面拍没拍进去。
- `camera`：拍下这一帧时镜头朝哪。`direction` 是相对站定朝向的方位（和场景的 `direction` 同一套词），`compass` 东南西北，`pitch` 是平视 / 略向上 / 向上 / 略向下 / 向下，`first_person` 第三人称（F5）时为 `false`。
- `toward`：只在给了 `id` 时有。`turned` 转过去并转到位了没有；没转或 2 秒没转到位时 `not_turned_because` 一句话，手上有活时写明目标编号和 `goal(operation=pause, goal_id=…)`、看完 `goal(operation=resume, goal_id=…)`。`framed`：`whole` 整个在画面里、`partly` 只拍到一部分、`hidden` 隔着东西看不见、`outside` 不在画面里；不是实体又只拍到一部分时 `step_back_blocks` 是按此刻的视野往后退约几格能整个装下。
- `in_picture`：画面里从镜头看得见的每个编号，`at` 是它在图上的像素位置 `[x, y]`（从左上角量）。种类字段与场景同名：实体 `type`（玩家另带 `name`），设施与告示牌 `block`，地形特征 `kind`，模组的东西 `category`；方位、距离不重复，要看去 `scene`、`detail`。图上最多标 24 个，按 `id` 指的、玩家、敌对、设施与告示牌与模组的东西、其他实体、地形特征的先后，同一档近的先；挤得放不下或超过 24 个的 `labeled=false`，`not_labeled_because` 写原因，照样列出。`unlabeled=true` 时全都 `labeled=false`、不写原因。隔着墙的不列。
- `menu_open`：开着界面时是哪种，取值同 `observe(menu)` 的 `kind`；没开不带。
- `summary`：一句话说转没转、装没装下、标了几个、有没有界面没拍进去。
- 同一时刻只拍一张，两次之间至少隔 1 秒，再快按 `busy` 回；游戏 1 秒内没画出新的一帧（窗口最小化）按 `unavailable` 回；`id` 认不出按 `unknown_id`，先认再转头，认不出不转。画面不写进世界记忆，也不进事件和目标结果。

## 8. 能力目录（草案）

v0 有约 50 个能力，粒度从"吃一口东西"到"拿到鞘翅"不等，好几组能力的结果互相重叠，能力说明一半中文一半英文。v1 的规则：

- **一个能力等于一个玩家能用一句话说清的意图**，并且有明确的完成标准；
- **两个能力的结果不重叠**；需要区分途径时，用参数（例如 `via`），不新开能力；
- **能力名不和 MCP 工具名、Minecraft 命令重名**，免得 LLM 分不清该调哪个；
- **长线目标由 LLM 规划**，不在 Mod 里写死。Mod 只提供 LLM 无法实时完成的部分（例如打龙时躲龙息、射水晶这类快速反应），Amaidesu 已有 `skills/progression` 这类攻略文档；
- 能力说明统一用中文（直播和解说都用中文），字段名用英文。

## 9. 迁移方式

- v1 从第一天起只提供本接口，不兼容 v0 的四个工具和 v0 的能力目录。
- Amaidesu 新增一个面向 v1 的 Minecraft Agent，通过配置在 v0 / v1 之间选择（Harness 本来就支持按配置选 Agent）。v0 的 Agent 原样保留，继续服务还没切换的直播类型。
- 能力目录随里程碑增长（04）。每加一个能力，接口快照的 diff、`CHANGELOG.md`、能力说明与随包技能同步更新；宿主的提示词与本地直播策略由宿主自己维护。

## 10 资源（resources）与技能

工具之外，服务器还发布一类只读资源：随包的玩法技能。技能回答“一类目标怎么一步步做成”，与能力说明（某个能力怎么调）、资料（世界里的事实是什么）分工。技能是文档，不是能力，也不替模型做决定；长线目标仍由模型规划。

### 10.1 握手

有技能可用时，`initialize` 的 `capabilities` 在 `tools` 之外多一个 `resources`（空对象），`instructions` 末尾多一句：

> 本服务器还发布玩法技能：用 `resources/list` 查看可用技能，用 `resources/read` 读 `skill://<分类>/<名字>/SKILL.md`；技能是参考，不授予额外权限。

暂不声明 `io.modelcontextprotocol/skills` 扩展：它要求 MCP `2026-07-28` 修订版与 `skills/list`、`skills/get`，当前服务器支持到 `2025-11-25`。在此之前，`skill://` 按普通资源发布，支持 `resources` 的客户端都能读；不支持 `resources` 的客户端拿不到技能。

### 10.2 `resources/list`

一次给全部当前适用的技能，不分页，按地址排序：

```json
{
  "resources": [
    {
      "uri": "skill://survival/survival-opening/SKILL.md",
      "name": "survival-opening",
      "description": "生存开局：从空手到有石器、食物、床和据点的稳定状态；新世界或身上几乎没东西时先读",
      "mimeType": "text/markdown"
    }
  ]
}
```

装了的联动模组没接上时，依赖它的技能不在列表里；这不是错误，也不拿相近的技能顶替。

### 10.3 `resources/read`

参数 `uri`，返回原样的 `SKILL.md`（含 frontmatter）：

```json
{
  "contents": [
    {
      "uri": "skill://survival/survival-opening/SKILL.md",
      "mimeType": "text/markdown",
      "text": "---\nname: survival-opening\n...\n---\n\n# 生存开局\n..."
    }
  ]
}
```

不认识的地址、或这项技能要的模组在本局没接上，按 JSON-RPC `-32602`（Invalid params）报错，消息写明没有这项技能。`resources/templates/list` 返回空列表，给每次连接都会问模板的客户端。

### 10.4 地址与门控

```text
skill://<分类>/<名字>/SKILL.md
```

- 分类是组织用的路径前缀：`survival`、`create`、`mekanism`、`progression`、`building`、`touhoulittlemaid`。
- 最后一段必须等于 `SKILL.md` 里的 `name`；读的人不用打开正文就能从地址认出技能名。
- 技能的 `metadata.requires-mods` 列出需要的模组 ID（逗号分隔）；这些模组 ID 在本局都登记为可用时，技能才进列表、可读。不按能力门控：能力在进世界时才登记，MCP 服务在启动时就起来了，按能力筛会让启动时的目录是空的。
- 不提供目录读取（`resources/directory/read`）：一篇技能只有 `SKILL.md` 一个文件。

### 10.5 技能文件

```text
assets/maicraft/skills/index.txt                 一行一个技能，写 <分类>/<名字>
assets/maicraft/skills/<分类>/<名字>/SKILL.md     一篇技能
```

`index.txt` 是唯一清单：没写进去的文件不发布；写了但文件不在、名字或分类对不上、frontmatter 不合法、地址重复，建技能库时直接失败。

frontmatter 是 YAML 的严格子集，只认三个顶层字段：

```markdown
---
name: create-machine-workflow
description: 机械动力机器从需求到产出：选工艺、查机器资料、写机器蓝图、先审再建、接动力、试运行验收；要造 Create 机器时读
metadata: {"requires-mods": "create"}
---
```

- `name` 用小写字母、数字、连字符，1–64 字，不能以连字符开头或结尾，不能有连续连字符，必须等于目录名。
- `description` 1–1024 字，先说是什么、再说什么时候读；它是 `resources/list` 里唯一的信息。
- `metadata` 是一行 JSON，值只能是字符串；`requires-mods` 是逗号分隔的模组 ID。没有前提时整个字段可以省略。
- 正文写给模型看，必须宿主中立：不出现“主播”“直播”“观众”“上报主播”，不出现宿主的工具名（`maicraft_lookup`、`minecraft_report`、`minecraft_notebook`）；引用工具用本服务器的短名（`lookup`、`execute`、`goal`、`events`、`observe`）。

### 10.6 宿主一侧

Amaidesu 保留一份本地“直播与上报”技能，写什么时候用 `minecraft_report`、直播节奏、观众体验、什么时候问主播、人格与口吻。玩法技能不再在宿主仓库里重复。

宿主连上服务器后读 `resources/list`，与本地技能合并，目录里标明来源；读正文走 `resources/read`，把读回的内容当外部输入、标明来自 MaiCraft；连接断掉时回退本地技能。技能正文里的 `lookup`、`execute`、`goal`、`events`、`observe` 对应宿主暴露的 `maicraft_lookup`、`maicraft_execute`、`maicraft_goal`、`maicraft_events`、`maicraft_observe`，由宿主在技能段里说明。
