# MaiCraftMod 实机测试

本项目的实机测试 = 通过 MCP 驱动游戏里的角色做事，用「任务终态 + 净变化对账」下结论。本 skill 只写跨机器通用的作业纪律；**本机的端点端口、启动配置、测试存档、目录约定一律查 `AGENTS.local.md`**（各开发者自备、不入库），与其冲突时以其为准。

## 角色边界（先读）

- 派出的验证会话**只走 CLI**：不启动客户端、不操作任何窗口。客户端由人或管家按本机约定的启动方式启动。
- 实机验收**全局串行**：一个客户端同一时刻只服务一个验证会话（多会话同世界互踩已实证）。
- 验证会话**不写本地账本**（账本由派单方记）；issue 只提建议不建档；临时文件只放本机约定的不入库目录。

## 启动与重启：先确认实机条件

- **用户已开好游戏并告知端点** → 直接连接（`init` + 自证即可），不要重启。
- **没开**则需要自己启动客户端。先判断在哪启动：一般在本机 Java IDE（如 IntelliJ IDEA）里已有 MaiCraft 客户端的运行配置，找现成的（有 IDEA MCP 时用 `get_run_configurations` 列出全部；没有就问用户本机有哪些配置）；若没有直进游戏存档的配置，经用户授权（顺带询问可用的测试存档是哪个）添加一个，做法如下。
- **在 IDEA 里加「直进存档」的客户端运行配置**：Run → Edit Configurations → 「+」→ Application；最稳的做法是复制现有「NeoForge Client」系配置，改四处——
  - **Program arguments**：`@<项目路径>\neoforge\build\moddev\clientRunProgramArgs.txt --quickPlaySingleplayer <存档目录名>`（args 文件由构建插件生成，不要手改；`<存档目录名>` 是 `saves/` 下的目录名，不是游戏内显示名）；
  - **Working directory**：`<项目路径>\neoforge\run`；
  - **Name**：带存档名（如「NeoForge Client 直进<存档>」）方便辨认；
  - 多客户端并行要钉端口时，VM options 加 `-Dmaicraft.mcp.port=<端口>`；不加则从 8766 起自动退让，先启的落 8766。
  - 创建时勾选「**Store as project file**」：配置才会落成 `.idea/runConfigurations/` 下的独立 XML（不勾只进 `workspace.xml`，机器私有、无法复制分享）。
- 运行配置有**两处存放**：`.idea/runConfigurations/*.xml`（共享的、一格一文件）与 `workspace.xml` 的 RunManager 段（每用户默认存放）——IDEA 下拉框显示的是两者的并集，文件数少于下拉框数是正常现象。**本仓库 `.idea` 整体不入库**：clone 下来没有现成配置，第一个须经上面的对话框创建（勾选 Store as project file 后即可复制分享）。
- **没有 IDEA MCP 时，直接操作配置文件**：共享的运行配置在 `.idea/runConfigurations/*.xml`，一格一文件。加一个直进配置 = 复制一份现有直进 XML（如 `NeoForge_Client_Smoke_005.xml`），改三处——`name` 属性、PROGRAM_PARAMETERS 里的 `--quickPlaySingleplayer <存档目录名>`、VM_PARAMETERS 里想钉的 `-Dmaicraft.mcp.port=<端口>`——然后**把文件里的项目绝对路径前缀（形如 `E:\…\MaiCraftMod\`，出现在 PROGRAM 与 VM 两处参数里）全局替换成本机路径**；WORKING_DIRECTORY 用的 `$PROJECT_DIR$` 本身可移植不用动。存盘后 IDEA 会自动识别（开着时实时装载，关着则下次启动生效）。只存进 `workspace.xml` 的个人配置不走这条路线：那是 IDEA 的状态文件，混着大量机器状态，改动须在 IDEA 关闭时做。
- 启动方式细节见 `AGENTS.local.md`（IDEA 运行配置或 `./gradlew :neoforge:runClient`；launch 参数带 quickPlay 可直进指定存档，省去手动进世界）。客户端内嵌 MCP 服务：端点在客户端本机，缺省从 8766 起、被占自动退让——本机实际端口表见 `AGENTS.local.md`。
- **触发启动**分两种情况：
  - 有 IDEA MCP：`get_run_configurations` 列配置 → `execute_run_configuration` 触发（数十秒超时属正常，游戏在后台继续起）。
  - 没有 IDEA MCP：请用户在 IDEA 里手动点启动（把要用的配置名告诉用户），或自己在终端**后台**跑 `./gradlew :neoforge:runClient`——注意 gradle 直起会停在标题界面，进世界需要人或 Computer Use 按两段式点击完成；之后的探活与握手流程完全相同。
- 重启两步：①优雅关停——对客户端进程发窗口关闭消息（PowerShell 的 `CloseMainWindow()`），走原版保存退出、几秒退净，**不杀进程**；②再启动。
- 等启动：编译 + 装载全部 mod 要几分钟，MCP 端口在客户端生命周期起来后才监听。用本 skill 自带的探活脚本等：`bash scripts/wait-for-endpoint.sh http://127.0.0.1:<端口>/mcp 720`（每 3 秒一次轻量 HTTP 探测，任何响应码即算活），端口通了再做**一次** `init`（此时应秒成）；脚本超时且无新崩溃才去读日志定位。手写 curl 循环（每 2~3 秒一次，任何响应码即算活）或每 30 秒盲试 `init` 也可，只是没有脚本省心。脚本依赖 bash+curl，Windows 用 Git Bash 跑没有问题；实在没有 bash 的环境，用 PowerShell 等价循环：`$end='http://127.0.0.1:<端口>/mcp'; $deadline=(Get-Date).AddSeconds(720); do { try { Invoke-WebRequest -UseBasicParsing -TimeoutSec 2 -Uri $end | Out-Null; 'endpoint is up'; break } catch { if ($_.Exception.Response) { 'endpoint is up (HTTP ' + [int]$_.Exception.Response.StatusCode + ')'; break } }; Start-Sleep -Seconds 3 } while ((Get-Date) -lt $deadline)`（成功与 4xx 都算端口已监听）。

## 崩溃与日志排查（另册）

读不到、起不来、装载失败时的完整排查流程在 **[crash-triage.md](crash-triage.md)**（同目录）：文件在哪、阅读顺序、常见类别处置表、真实案例对照。速查三条：

- 崩溃报告只认重启之后的时间戳；
- 装载期先看 `crash-reports/` 最新 fml 报告的「Mod loading issue」逐条清单（一次报全，修一个不等于只剩一个）；
- 挪问题 jar 进备份目录不删，一次只改一个变量再重启。
- **崩溃报告只认重启之后的时间戳**——历史崩溃文件是干扰源，已两次把验证会话带偏。
- 改过实例配置（如 `config/maicraft.json` 的开关）或拉取过新代码后必须重启才生效（配置启动时读一次）。

## 连接与 CLI 纪律：优先自带 MCP，未注入才走 CLI

- 会话若已注入本项目的 MCP server（`maicraft` 的 execute / observe / lookup / goal / events 工具），**优先直接用它们**，它们天然连着已配置的端点；只有未注入时（常见于派出的子会话）才用 `tools/maicraft_cli.py`。
- 走 CLI 时：MCP 端点**每次调用显式带**，多客户端并行时缺省会静默打到错误实例。
- 每个会话独立 `--session-file`；游戏重启后先 `init` 重握手。
- **含中文的参数一律 `@file` UTF-8 载荷**——命令行直传中文会被转码弄乱。
- 握手成功后先 `observe(self)` 自证：坐标、群系、维度、血量饱食，与世界对得上再开工；客户端空闲跑了很久后角色状态未知（它自己吃饭睡觉搬过家），别按记忆里的位置开工。
- 等待游戏内任务一律感知等待（wait_ms），**禁止无人看守的 sleep**——等待期间角色可能被怪打、溺水。出危险先自救；角色死亡如实回报并停手，死亡不算验证结论。

## 证据标准

- 每个结论 = **任务终态 + 背包/世界净变化对账**，两样齐；回执的成败状态只是线索，不是裁决。
- 观测性坑：自身位置的读取有数秒级滞后；长等待偶发传输报错（重试即好）；服务端读数类接口可能滞后一拍（读两次再下结论）。
- 事件流「有始必有终」：插曲类事件（自卫、吃饭、夜宿）开始与收场要成对核对，缺收场本身是缺陷。

## 生存模式优先，命令只搭环境

- 实机测试通常在**生存模式**下进行：创造模式会绕过伤害、饥饿、掉落这些被验证的行为，有些内容测不出来。验证前确认玩家是生存模式（用户用命令造完环境后可能停在创造）。
- 游戏命令**只用于搭建测试环境**且需用户授权；未经授权不得用命令作弊——不用命令替角色完成被验证的事，也不用命令清掉路上碰到的障碍。
- 开关指南：`config/maicraft.json` 的 `allowGameCommands`（默认 false）置为 true 并重启客户端后，`chat` 能力发的 `/` 命令才会执行；不开则命令被如实拒绝。
- **给在跑的目标发命令 = 替换它**：替换会如实报告停点，但目标不可恢复——别用替换去催进度，也别指望「暂停中插一条命令」能回到原目标。
- 生存临时任务（夜宿自保、吃饭、自卫）占身体期间，目标是**在等、不是卡**：查询会如实说「临时任务「…」占着角色，要等它做完才接着推进」。临时任务不出现在目标列表里。
- 命令若停在初始决定步骤：先查目标详情看 doing，区分「在等」与「真卡」，把原话带回。

## 已知坑速查

| 坑 | 处置 |
| --- | --- |
| 历史崩溃报告冒充本次失败 | 只认重启时间戳之后的报告 |
| 命令行直传中文乱码 | 全走 @file 载荷 |
| 推送钩子构建全绿后传输断（GitHub 瞬断，屡发） | 看远端引用是否前移判定成败，重试即可 |
| 暂停/夜宿中下新目标 = 替换 | 催天亮等场景别用新目标；等自然推进 |
| 生存临时任务占身体整晚是设计行为 | 用查询措辞区分「等」与「卡」 |
| 来源类失败可能被无视而逐刻重试（现象：界面反复开关） | 记下现场、目标与角色位置，回报派单方 |
| 夜里 travel 不夜宿（无床不停稳） | 夜宿样本需已知的床或安顿点在场才取得到 |
| 白天用僵尸做战斗样本会晒烧自灭 | 战斗样本换尸壳（husk）等不晒烧的敌对生物 |
| 夜间/雨天游戏刻可能拖慢，「还有几分钟天亮」类估计失真 | 以事件流与实际推进为准，不以估计计时 |
| 验证会话中途自己下达了新目标把在跑目标替换掉 | 场景脚本里写明「中途不下任何新目标」；复盘先核对自己 |

## 回报格式

逐项：场景构造、关键调用（命令原话）、对账、结论（通过 / 失败 / 受限未能测+原因）。全局：世界与角色状态、动过什么（含命令对世界的改动）、有无新崩溃、卡住目标的编号。受限不是失败——如实分开写，别冒充也别漏报。
